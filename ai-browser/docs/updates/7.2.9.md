# AI Browser 7.2.9

The October 9 diagnostics contain identical exports of 6,626 events; 1,357 belong to 7.2.8. In those events, AI requests repeatedly reached the enforced 120-per-day limit while hourly usage remained below 30. There were 765 opportunity rechecks, including 610 with no target on results, and 101 lesson outcomes: 68 partial, 32 failed, 1 done. This is limited progress, not evidence that the brain has mastered these sites.

## Controls

Allow AI help remains the master switch. With both new boxes unchecked, the app retains its capped behavior (30 requests/hour, 120/rolling day) and configured provider/model. The two new opt-in boxes are persisted on the device and start unchecked:

- Unrestricted regular AI: standard OpenAI uses the existing pinned GPT-5.4 mini model with no reasoning. Other providers/custom endpoints keep their configured model.
- Unrestricted smarter AI: standard OpenAI uses pinned GPT-5.4 with medium reasoning and a larger output ceiling. More expensive. Requires standard OpenAI configuration. Takes priority when both boxes are checked.

Both remove hourly and daily app request caps and stay selected until unchecked. They do not remove the master off switch, per-lesson request limit, failure cooldowns, authentication holds or provider limits. Requests and reported token usage remain durably counted before transport, including failures. Corrupt accounting still prevents new calls. Turning off AI prevents new transports; a request already sent may finish.

The usage display now shows real rolling counts and the current cap mode; stale /6 and /24 denominators are removed. The legacy 24-hour stronger trial no longer overrides configuration. Both new boxes start unchecked; upgrading does not silently enable unrestricted spending.

## Pagination discovery

When an unfinished pagination lesson has no visible next/load-more control but results can scroll further, the learner can make up to 12 verified discovery scrolls within the existing 16-action task budget. This reaches deeper footers before source rotation reloads the results page. The repeat guard recognizes observed scroll movement but still bounds stalled retries. Its postcondition verifies movement only; this never completes pagination. Actual next/load-more still requires verified results. At the bottom, busy states, dialogs and authentication boundaries do not create this target. Site rotation and retry limits remain in force.
